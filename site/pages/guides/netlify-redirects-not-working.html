Netlify redirects not working: causes and fixes.

The rule is usually fine. It is in the repo and not in the deploy, or another rule matched first, or a real file is sitting on that path. Netlify’s docs describe all three.

The order Netlify uses

Rules can live in a plain _redirects file in the publish directory, or in one or more [[redirects]] tables in netlify.toml. For a request, Netlify uses the first matching rule, top to bottom. _redirects is processed before netlify.toml. Edge functions run before either of them.

Paths are case-sensitive. Characters that are special in a path have to be URL-encoded. A line that starts with # is a comment. If you omit the status, the default is 301.

The line 404less copies for Cloudflare Pages and Netlify is the same shape. For /docs/old → /docs/new the dashboard emits: 

# _redirects (Cloudflare Pages / Netlify)
/docs/old  /docs/new  301

Fields are separated by whitespace. Netlify’s own examples use wide gaps.

The file never made it into the publish directory

Netlify reads _redirects from the folder you deploy, after the build. A copy that sits next to your source and is gitignored out of dist/ or public/ does nothing. Generators that skip files beginning with _ do the same. Netlify calls out Jekyll: add an include for _redirects in _config.yml, or the file is dropped.

After the deploy, open the published-files list (or curl -sI https://yoursite.example/docs/old) before you rewrite the rule. A rule that is not in that deploy cannot fire.

A broader rule already matched

This is the usual “netlify redirects not working” file on a single-page app. The catch-all rewrite is first, so the specific 301 under it is dead: 

# matches every path, including /docs/old
/*            /index.html  200
/docs/old     /docs/new    301

Specific rules go above the splat:

/docs/old     /docs/new    301
/*            /index.html  200

The same ordering applies inside netlify.toml, and a rule in _redirects still beats a later rule in the toml file. Role, country, language, and query conditions only match when they match. A rule that requires query = {id = ":id"} will not run for a request that has no id.

A 200 is a rewrite: the address bar stays put and the server sends different HTML. That is what you want for an SPA fallback. It is also how a missing URL becomes a soft 404 if the fallback is your app shell. See fixing soft 404s. Netlify will serve a 404.html from the publish directory for paths that do not resolve, with no rule required, as long as no earlier rewrite claimed the path.

A real file is shadowing the rule

By default a redirect does not replace a file that already exists at that path. Netlify calls this shadowing. Force it with ! on the status in _redirects, or force = true in toml: 

/docs/old   /docs/new   301!
[[redirects]]
  from = "/docs/old"
  to = "/docs/new"
  status = 301
  force = true

Force is the right fix when an old index.html is still being built. It is the wrong fix when the splat above is the thing matching: forcing a rule that never runs changes nothing.

Status codes that surprise people

  • 301 is the default. Permanent. The address bar changes.
  • 302 is the temporary code Netlify tells you to use. Their options doc says 307 is unsupported.
  • 200 rewrites. The address bar stays.
  • 404 can point a path at a custom error page. The address bar stays. Because of shadowing, that page is returned when no asset exists there.

Pretty URLs and trailing slashes are documented further down the redirect-options page. This draft does not copy that section.

Past about 10,000 rules Netlify says the serialized redirect blob can fail the deploy, and they recommend splats or Edge Functions. There is no need to pre-empt that on a docs site with a few dozen old URLs.

Related tool: redirect rule generator and redirect chain checker. Both paths may 404 until the tools PR lands. A chain is worth checking: Google follows a limited number of hops and indexes the final URL. The migration checklist is the place for a pile of old paths.

Cloudflare Pages speaks a similar file, with different rules

Pages also uses _redirects, and the 404less snippet comments it as “Cloudflare Pages / Netlify”. The defaults differ. Pages uses 302 when you omit the code, so the snippet writes 301 on purpose. Pages follows the redirect even when a file exists at that path. Pages does not support Netlify’s query conditions or a 404 status in that file. Caps and the rest are in the Cloudflare Pages guide.

Vercel does not read this file. permanent: true there is a 308. That is the Vercel redirects guide.
