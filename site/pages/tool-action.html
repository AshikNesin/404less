GitHub Action

Fail CI when the crawler finds broken links

The crawler already ran. This workflow asks your 404less instance for open broken links and fails the job when the list is not empty. Resolved links stay green. There is no second crawl inside GitHub.

The workflow

Save it as .github/workflows/broken-links.yml. The same file is in the repo at docs/examples/broken-links.yml. Create a team API key in 404less (it starts with 404l_) and three repository secrets:

  • FOURLESS_URL — the Worker origin, no trailing slash, such as https://404less.example.com
  • FOURLESS_KEY — the team API key
  • FOURLESS_SITE_ID — the site id from the dashboard URL
name: Broken links
on:
  schedule:
    - cron: "17 6 * * 1"
  workflow_dispatch:
jobs:
  broken-links:
    runs-on: ubuntu-latest
    steps:
      - name: Fail if the crawler has open broken links
        env:
          FOURLESS_URL: ${{ secrets.FOURLESS_URL }}
          FOURLESS_KEY: ${{ secrets.FOURLESS_KEY }}
          FOURLESS_SITE_ID: ${{ secrets.FOURLESS_SITE_ID }}
        run: |
          set -euo pipefail
          curl -fsS \
            -H "Authorization: Bearer $FOURLESS_KEY" \
            "$FOURLESS_URL/api/v1/sites/$FOURLESS_SITE_ID/links?status=open&limit=100" \
            -o links.json
          node --input-type=module -e '
            import { readFileSync } from "node:fs";
            const data = JSON.parse(readFileSync("links.json", "utf8"));
            const links = data.links ?? [];
            if (!links.length) {
              console.log("No open broken links.");
              process.exit(0);
            }
            console.error(links.length + " open broken link(s) the crawler is still tracking:");
            for (const link of links) {
              console.error("- " + link.hits + " hit(s)\t" + link.url);
            }
            process.exit(1);
          '

The schedule is Monday morning so it reads whatever the daily crawl wrote. workflow_dispatch is already there, so you can run it from the Actions tab without waiting. It calls GET /api/v1/sites/:id/links?status=open, which is the same list the dashboard shows. Ignored and resolved rows are not in it.

“New” here means currently open. A link you have marked resolved does not fail CI. A link the crawler reopened, because visitors hit it again or the crawl saw a 404, does.

What this does not do

It does not crawl the pull request’s preview. The public broken link checker is capped at 60 pages and rate limited, so a CI job that called it would flake. Host 404less, point the crawler at the site, and let CI read the result.

The API key is a bearer token for that team. Store it as a secret. Don’t print links.json if the URLs themselves are sensitive; the failure log lists the URL and the hit count, which is the point of the check.

Questions

The job fails on links I already know about.
Mark them ignored in 404less if they are not yours to fix (a partner site, a mailto rewrite). Ignored rows stay out of this query. Resolved rows come back only if the URL breaks again.
Can a pull request fail before the crawl has run?
Only on links that are already open. A brand-new 404 in the pull request is invisible until the crawler, or a visitor, sees it. Run “Crawl now” on the preview if you need this check on the PR itself, and point FOURLESS_SITE_ID at that site.
Why not lychee or a curl loop?
Those crawl the repo from zero on every run. This one reuses the crawler you already scheduled, including redirect chains and the 404s a crawl never sees because only a visitor requested them.

The crawler has to be yours.

Deploy 404less, add the site, and the workflow above reads what the crawler stored. Cloudflare’s free tier covers a personal instance.
